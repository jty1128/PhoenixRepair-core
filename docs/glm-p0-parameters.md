# GLM-5.2 P0 模型与运行参数详解

核对日期：2026-11-09。本文解释当前仓库 `our_method.sh` 的 GLM-5.2 P0 配置，不代表历史所有实验都采用这些参数，也不代表 API 服务商允许的最大规格。

P0 指作者 agent 首次完成提交的补丁。当前入口生成 P0 后结束，不运行独立 reviewer、审查后修复或 P1 选择；“提交完成”也不等于“官方评测通过”。

## 1. 参数总览

| 参数 | 当前 GLM-5.2 P0 设置 | 作用范围 |
| --- | --- | --- |
| API 模型 | `glm-5.2` | author 与 P0 summary |
| API 协议 | DashScope OpenAI-compatible Chat Completions | 模型请求 |
| Thinking | `enable_thinking=false` | author 与 P0 summary |
| temperature / top_p | `0.0 / 1.0` | author 与 P0 summary |
| 工具选择 | `tool_choice=required` | author；summary 不携带同一套工具 |
| 单次输出上限 | `32,768 tokens` | author 与 P0 summary |
| 输入检查上限 | `131,072 tokens` | author 的本地请求检查 |
| 上下文压缩 | 超过 `120,000`，目标 `110,000`；保留首尾各 5 个工具交互轮次 | author 请求路径 |
| P0 API 调用上限 | `200 次` | 每题候选、summary、final 共享 |
| 轨迹步数上限 | `200 步` | 单个 author 阶段，恢复继承已用步数 |
| author 阶段累计时限 | `7,200 秒` | 每个 author 阶段，恢复不重置 |
| author 单次 API 超时 | `240 秒` | 单次模型请求 |
| author 同一 query 尝试上限 | `8 次`，包含首次 | 仅对可重试 API 错误 |
| 重试等待 | 随机指数退避，参数范围 `10–120 秒` | 相邻重试之间 |
| SDK 自动重试 | `num_retries=0` | 避免 SDK 另行增加重试 |
| P0 summary 请求上限 | `1 次` | 多候选任务才运行 |
| P0 summary 超时 | 连接 `30 秒` / 读取 `240 秒` | summary 的 HTTP 请求 |
| 默认任务并发 | `4` | 同时处理的不同任务 |

**输入检查、工具选择、上下文压缩不能机械地套用到 summary。** summary 使用独立 HTTP 请求路径；当前实现没有调用 author 的本地输入计数与压缩流程。详见第 9 节。

## 2. 模型名、接口协议与 Thinking

`glm-5.2` 是请求中实际指定的模型名称。DashScope OpenAI-compatible 表示使用兼容 OpenAI Chat Completions 的请求格式，接口路径为 `/chat/completions`，不是调用 OpenAI 的模型。

`enable_thinking=false` 是请求服务端关闭该接口的 thinking 模式。它不表示模型不分析问题，也不禁止普通响应中出现分析文字。不能仅凭响应较长就认定 thinking 已开启。

author 使用模型读取源码、提出操作、修复代码并提交。多候选时，summary 使用同一模型比较候选，不切换到另一模型监督。

## 3. temperature=0 与 top_p=1

- `temperature=0`：减少采样随机性，倾向选择概率最高的输出。
- `top_p=1`：不额外缩小累计概率采样范围。

两者控制输出采样方式，不控制执行步数或输出长度。即使参数固定，也不能承诺多次运行的补丁逐字一致：工具输出、环境状态、请求响应及服务端执行差异都可能影响后续轨迹。

## 4. author 的 tool_choice=required

在携带工具定义的 author 请求中，`required` 要求模型返回工具调用，而不是只给一段普通文字。模型通过工具读取、编辑、执行命令或提交。

它不要求模型每次修改代码，也不保证选择的工具或参数正确，更不保证不会重复调用工具。

执行一次工具本身不额外占一次模型 API 调用；将工具结果交回模型、请求下一步响应时，才会产生新的模型调用尝试。工具运行耗时仍受执行时限管理。

## 5. 单次输出上限 32,768 tokens

这是**每一次模型响应的最大输出长度**，不是每道题的总输出量，也不是要求每次输出都写满。

输出可以包括普通文本和工具调用参数，例如编辑命令中的代码。模型可以提前结束；如果达到输出上限，响应可能不完整，需要查看实际结束原因与后续处理。

当前 GLM P0 的 author 和 summary 输出上限均默认为 32,768，分别读取 `max_tokens` 和 `summary_max_tokens`。两者可独立配置；修改 author 的上限不会自动修改 summary。

例如，某题发出 60 次 API 请求，每次实际输出长度都可以不同。因此：

- 32,768 不是该题累计输出上限。
- 200 次 API 调用不是固定 token 消耗或固定费用。
- 提高输出上限只是放宽单次响应空间，不会自动修复错误定位、遗漏需求或无效验证。

## 6. 输入上限 131,072 tokens

author 在请求前对待发送消息进行本地 token 估算。消息包括系统提示、题目、定位指导，以及此前的对话和工具结果；不是把整个仓库一次性全部发送给模型。

如果经过可用的上下文压缩后，估算输入仍超过 131,072，代码会抛出上下文超限错误。

需要区分三个概念：

1. **输入上限**：本地允许传入一次请求的估算消息长度。
2. **输出上限**：这次请求允许模型生成的最大响应长度。
3. **服务端上下文限制**：由实际接口决定，还可能考虑工具定义、协议开销或输入输出的组合。

因此，配置中同时写了 131,072 输入和 32,768 输出，不能据此推断服务端一定接受二者同时取满，也不能把它当成服务商规格声明。本地估算与服务端计数也可能存在差异。

## 7. 上下文压缩：120,000 → 110,000

author 请求的估算输入**超过 120,000 tokens** 时，尝试压到目标 110,000，以留出后续交互空间。

当前压缩不是另请模型总结整段对话，而是程序对中间较长的工具输出做抽取：保留开头、结尾，以及部分错误或结果行，用较短摘录替换本次请求中的完整输出。动作及工具调用 ID 保持不变。

- 保留最前 5 个和最后 5 个工具交互轮次中的输出，不压缩这些位置。
- 优先处理中间较长的工具输出，达到目标后停止。
- 不把全部中间对话删除；没有压缩价值的短输出可能保持原样。
- 操作的是请求消息副本，不覆盖完整历史记录。
- 此压缩不调用模型，因此不增加模型 API 调用次数。

**110,000 是目标，不是保证。** 如果可压缩内容不足，结果可能仍大于 110,000；随后仍按 131,072 的输入上限检查。压缩会省略内容，所以可能影响模型后续对细节的利用，不能把它视为完全无损。

## 8. 200 次 API 调用与 200 步的区别

### 每题共享的 200 次 API 调用

这 200 次用于生成 P0，包含候选 author、多候选 summary 和 final author。定位单独计预算，不在其中。

| 候选数量 | API 调用次数分配 |
| --- | --- |
| 1 | author 最多 200 次，直接提交 P0；无 summary 和额外 final |
| 2 | 候选各最多 50 次；summary 最多 1 次；final 使用剩余次数 |
| 3 | 候选最多 34 / 33 / 33 次；summary 最多 1 次；final 使用剩余次数 |

```text
final 可用 API 调用次数
  = 200
  - 所有候选已计入预算的 API 调用次数之和
  - summary 已计入预算的 API 调用次数
```

例如，两个候选分别用了 30 和 40 次，summary 用了 1 次，则 final 最多还能使用 `200 - 30 - 40 - 1 = 129` 次。正常完成 summary 并进入 final 时，至少保留 99 次 API 调用。final 从原始代码开始，参考 summary 重新生成补丁，不直接继承某个候选的工作目录。

所有数字均为上限。提前完成就可以提交，不要求为了用完次数继续运行。

### 单条 author 轨迹的 200 步

轨迹步数是 agent 执行循环中记录的步骤数，不是 HTTP 请求次数。一次普通交互通常涉及请求模型和执行操作，但 API 内部重试不一定形成新的轨迹步骤。

例如，同一步先遇到两次网络失败，第三次才成功，这一步已经消耗 3 次 API 调用尝试。因此可能在 200 步之前先耗尽 200 次 API 调用。

`max_steps: 200` 在当前框架同时用于确定 P0 共享调用预算和 author 步数限制；两者仍是独立计数。多候选中的一个 author 虽有 200 步配置，但还受其分配到的 50 次或 34 次等 API 调用上限约束。

### 失败与恢复如何计数

计数在每次模型调用尝试前持久化。失败请求、重试以及结果未知的已发出请求都保留消耗；恢复不重新发放 200 次。

所以这里不是“200 次保证成功的模型回复”。API 调用预算也是框架的执行计数，不能直接当作服务商实际计费请求数：失败请求是否计费、消耗多少 tokens，需要以 usage 和账单为准。

## 9. P0 summary 的特殊规则

summary 仅在多候选时运行，作用是比较当前任务生成的候选补丁，提供最终生成指导；它不是官方评测器，也不证明被推荐的方案正确。

当前设置如下：

- 使用同一 `glm-5.2`，thinking 关闭。
- `temperature=0`、`top_p=1`、输出上限 32,768 tokens。
- 最多 1 次请求，占用该题共享的 200 次 API 调用之一。
- 连接超时 30 秒，读取超时 240 秒。
- 不套用 author 的“同一 query 最多 8 次尝试”。

summary 通过独立 HTTP 路径发送题目、候选补丁及比较提示，**没有安装 author 的工具调用流程，也没有调用 author 的 131,072 本地输入检查和 120,000 → 110,000 压缩函数**。当前 P0 summary 会使用完整候选补丁；候选合计很长时，不能假设框架一定会自动压缩到 author 的目标值。

30/240 秒分别控制建立连接和读取等待，不能简单相加后理解为“整个 summary 必定最多运行 270 秒”。整个任务也不由这个超时参数单独控制。

## 10. 三类时间设置不能混用

### author 单次 API 超时：240 秒

这是传给模型客户端的单次 API 超时配置，用于限制请求等待。它不是该题所有 API 请求的累计时间，也不是工具命令的执行超时。失败后若错误可重试且仍有预算，框架可以再次尝试。

### author 阶段累计时限：7,200 秒

7,200 秒等于 2 小时。控制器对一个 author 阶段的工作进程累计运行时间进行管理，包含模型等待和该阶段中的工具执行等开销，不只统计模型输出时间。恢复时扣除该阶段已经使用的时间。

多候选时，每个候选 author 与最终 author 各自受阶段时限约束。因此，**不是整道题“定位 + 全部候选 + summary + final”合计只能运行 2 小时**。所有候选与 final 依然共享同一题的 200 次 API 调用预算。

基础设施检查、阶段间调度及确定性的提交恢复另有生命周期控制，因此 7,200 秒也不应作为整条实验从启动到结束的精确墙钟上限。

### 重试退避：10–120 秒

遇到可重试 API 错误后，使用随机指数退避等待，避免连续高频重试。该等待与单次 API 超时不同；重试会继续受到剩余 API 调用次数和阶段时间限制。

## 11. 最多 8 次尝试与 num_retries=0

author 对同一个 query 最多尝试 **8 次，包含首次，即最多再试 7 次**。不是失败后再试 8 次，也不是每题只允许 8 次 API 调用。

代码区分错误类型：超时、网络连接异常，以及 HTTP 408、429、5xx 等可以重试；鉴权、参数、证书等需要修正配置的问题不靠重复发送同一请求解决。

`num_retries=0` 关闭 SDK 这一层的自动重试，外层框架仍按上述规则处理重试，避免多层重试叠加导致实际请求数难以追踪。

例如，某个 query 连续失败 7 次、第 8 次成功，计入 8 次 API 调用。若开始前只剩 3 次可用 API 调用，就不能无视总预算发满 8 次。

耗尽内部重试后，框架保存中断补丁和轨迹；符合恢复条件时可以有界续跑，但继续沿用已经消耗的调用、步数和时间。API 中断不能被改写成“正常提交成功”。更多细节见 [恢复规则](recovery.md)。

## 12. 并发数 4

默认并发数 4 指同时推进最多 4 个不同任务，不是每道题同时开 4 个候选，也不表示任意时刻一定有 4 个 API 请求正在执行。

同一道题的候选、summary、final 按阶段顺序执行。任务在准备容器、运行命令、等待重试或请求准入时，实际同时进行的 API 请求可能少于任务并发数。

并发数影响总吞吐、API 限流风险和机器资源压力，不会把单题 200 次 API 调用预算乘以 4。

## 13. 定位参数独立，不能照搬 patch 参数表

默认定位最多 150 步，可通过 `--localization-max-steps` 调整，当前参数校验最多允许 200 步。可通过 `--locations` 复用已有同模型定位，跳过重新生成定位。

定位使用自己的配置：输出上限 32,768、API 超时 600 秒、工具选择 auto、thinking 关闭；压缩触发值 100,000，目标 90,000，压缩后的输入还受 110,000 检查限制。它与 author 的 required、240 秒及 120,000 → 110,000 压缩设置不同。

定位消耗的 API 调用与 tokens 仍属于整个方法的实际成本，只是不占后续生成 P0 的 200 次 API 调用。比较方法总成本时，不能把定位成本漏掉。

## 14. 配置入口与实现依据

`bash our_method.sh --model glm5.2` 自动选择 `configs/models/glm-5.2/our_method.yaml`，无需手动指定 `--config`。`--dry-run` 展示最终生效的配置与请求参数。

- P0 共享 API 调用上限通过 `max_steps` 确定，同时影响 author 步数设置。
- author 输出上限使用 `max_tokens`，可用 `--max-tokens` 覆盖；summary 使用独立的 `summary_max_tokens`，可用 `--summary-max-tokens` 覆盖。
- 输入检查和压缩参数可通过对应配置项设置。
- `--locations` 选择已有定位，不改变生成阶段的 API 调用计数规则。
